# 乌兰察布本地生活知识图谱

把乌兰察布 6,949 个本地生活 POI 做成一张**可对话的知识图谱**:自然语言提问 →
双引擎(GraphRAG)检索 → 带推理路径和来源标注的回答。

数据源:高德开放平台 Web 服务 API(POI 搜索),个人学习用途。

---

## 一、架构

```
用户提问
   │
   ├─ ① 精确缓存命中?  ── 是 ─→ 直接返回(毫秒级)
   │      否
   ├─ ③ 语义缓存命中?  ── 是 ─→ 返回(标注相似度)
   │      否
   ├─ 对比意图?        ── 是 ─→ 对比分析(表 + 条形图)
   │      否
   └─ GraphRAG 双引擎检索
          ├─ 规则分流(0 次 LLM 调用)
          ├─ 图谱路:Text2Cypher → Neo4j   ┐ 并行
          ├─ 向量路:BGE-M3 → numpy 相似度  ┘
          ├─ 合并:图谱优先 + 向量补位去重
          └─ LLM 流式生成回答(带推理路径/来源/反馈)
```

**为什么是双引擎**:结构化问题(「人均 50 以下」「有多少家」)需要精确过滤和计数,
向量检索做不了;语义问题(「想涮点肉吃」)没有可直接翻译成 SQL/Cypher 的条件,
图谱只能靠关键词匹配。两者盲区互补,合并后在混合类问题上明显更好——
第三节的评测数据是这个判断的依据。

### 关键技术选择

| 选择 | 备选 | 理由 |
|---|---|---|
| **numpy 暴力检索** | Milvus / Chroma / FAISS | 6,949×1024 的矩阵乘在 CPU 上 <10ms,量级根本用不上 ANN 索引。`scripts/bench_vector.py` 做过对照实验(见下) |
| **Neo4j 存缓存与反馈** | Redis / MongoDB | 线上是 Streamlit Community Cloud,容器文件系统是临时的;Aura 是唯一可用的持久化存储 |
| **LLM 当 Reranker** | BGE-Reranker 模型 | 云端 1GB 内存装不下 2GB 的 reranker;候选只有十几条,LLM 精排够用 |
| **规则分流** | LLM 意图分类 | 规则 0 毫秒、0 成本、行为可预测;实测分流准确率足够,还省掉一次 LLM 往返 |
| **线程池并行** | asyncio.gather | 两路都是同步 HTTP 调用,改 async 要重写整条链路,收益一样但风险大得多 |

## 三、评测:三套方案对比

评测集 `data/eval_set.json` 由 `scripts/build_eval_set.py` **从真实图谱反推生成**,
100 题分三类(A 结构化 40 / B 语义化 30 / C 混合 30),每题的
`ground_truth_cypher` 可以独立重跑验证。评测脚本 `scripts/eval_rag.py`
直接调用线上同一套代码路径,不另写实现。

两个指标一起看:

- **P@5** — 返回的前 5 条里,有多少条真的满足这道题的条件。
  衡量"有没有理解意图",与排序无关。
- **R@5** — 该条件对应的全部商家中,Top-5 覆盖了多少。

> 为什么不用"标准答案是否出现在 Top-5"做唯一指标:标注的标准答案是
> "满足条件且按评分排序的前 10 家",而向量检索按语义相似度排序。
> 排序依据不同,即使返回的全是正确品类的店也会被判成未命中——
> 这个指标实际在比对排序方式,而不是回答质量。

### 结果

| 方案 | 严格命中 | **P@5** | R@5 | A 结构化 | B 语义化 | C 混合 | P50 | P95 |
|---|---|---|---|---|---|---|---|---|
| 纯图谱 | 56.0% | 54.1% | 53.4% | **81.0%** | 36.7% | 35.6% | 1,496 ms | 3,159 ms |
| 纯向量 | 34.0% | 48.8% | 49.0% | 66.0% | **56.7%** | 18.0% | **334 ms** | **520 ms** |
| **GraphRAG** | 49.0% | **59.6%** | **58.9%** | 79.5% | 53.3% | **39.3%** | 1,401 ms | 3,205 ms |

**这组数据说明了什么**

1. **各有一块对方够不着的盲区。** 结构化问题上纯图谱 81.0% 对纯向量 66.0%(高 15 个点);
   语义问题上反过来,纯向量 56.7% 对纯图谱 36.7%(高 20 个点)。
2. **混合类问题上融合确实最好。** GraphRAG 39.3%,比纯图谱高 3.7 个点、比纯向量高 21.3 个点。
3. **总体上融合也最好。** 总 P@5 59.6%,高于两个单路。
4. **但向量快 4 倍。** 纯向量 P50 334ms,GraphRAG 1,401ms —— 差距主要是图谱那路的
   Text2Cypher(一次 LLM 往返 1.5–2s)。所以纯语义类问题会短路跳过 Text2Cypher(见 4.4)。

**这些数字为什么不"漂亮"**

文档给的示意值是 68% / 71% / 89%,实测低不少。原因值得说明:

- **判定标准很严**:返回的前 5 条里,必须真的满足这道题的全部条件
  (区县 + 人均阈值 + 品类 + 排序)。LLM 生成的 Cypher 经常差一个条件,
  比如把"人均 100 以下"写成"评分 3.8 以上",结果整批都不算命中。
  这恰恰是真实系统里最常见的失败模式,不该被一个宽松的判定掩盖。
- **`answerable` 全为 true**:没有排除那些图谱本来就不支持的问法。
- **B/C 类的标准答案是"文档化谓词命中的集合"**,属于词法层面的代理标注,
  是真实语义质量的下界,不是人工精标。

> 不把示意值当结果是这个项目里最容易做错的事。上面每一个数字都可以用
> `python scripts/build_eval_set.py && python scripts/eval_rag.py` 重跑出来,
> `data/eval_report.json` 里存了每一道题的 Top-5 返回和标准答案。

## 四、性能优化的实测数据

每一项都有可复现的测量,不是估计值。

### 4.1 Neo4j 连接池复用:单次查询省 ~2.4 秒

优化前,每个模块各建各的 driver(`llm_qa` / `feedback` / `graphing` / `reasoning_path`…),
每次调用都要重做 DNS + TCP + TLS 握手。线上是 Aura,这个开销尤其明显。

| | 单次查询耗时 |
|---|---|
| 优化前(每次新建 driver) | **2,629 ms**(中位,5 次) |
| 优化后(全局连接池复用) | **250 ms**(中位,5 次) |

一次问答里 `run_cypher` 会被调用多次(Text2Cypher 执行、失败重试、推理路径回溯、
品类清单、缓存写入),这项修复是所有性能项里收益最大的一个。

> 复现:`python -c "from src.db import run_cypher; ..."`,见 `src/db.py` 顶部注释。

### 4.2 Neo4j 索引:扫描行数 6,949 → 21

优化前三种高频查询全是 `NodeByLabelScan`(全表扫 6949 行)。

| 查询形态 | 优化前 | 优化后 |
|---|---|---|
| 按评分排序 | `NodeByLabelScan` 扫 **6,949** 行 | `NodeIndexScan` 扫 **21** 行 |
| 按人均过滤 | `NodeByLabelScan` 扫 **6,949** 行 | `NodeIndexSeekByRange` 扫 **21** 行 |
| 店名 CONTAINS | `NodeByLabelScan` 扫 **6,949** 行 | 见下 |

> 复现:`python scripts/apply_indexes.py --bench`

**踩坑一:CONTAINS 用不了 RANGE 索引。** 提示词强制 LLM 用 `CONTAINS` 匹配店名
(库里店名带后缀,如「乌兰图雅·蒙餐(乌兰察布怡海佳苑店)」),而 `CONTAINS` 是子串匹配,
RANGE 索引只加速 `=` 和 `STARTS WITH`。所以店名那一行优化后**没有变化**。

**踩坑二:全文索引必须指定 cjk 分析器。** 换成 `FULLTEXT` 索引后,
默认的 `standard` 分析器按空白/标点切词,中文店名整串会变成一个 token——
搜「蒙餐」匹配不到「荣茂蒙餐」,召回结果和 CONTAINS 完全对不上。
加上 `fulltext.analyzer: 'cjk'` 后召回才对齐:

| 关键词 | CONTAINS | FULLTEXT(cjk) | 召回率 |
|---|---|---|---|
| 蒙餐 / 蜜雪冰城 / 莜面 / 烧麦 / 羊杂 / 烧烤 | 36–124 | 完全一致 | 100% |
| 乌兰图雅 | 2 | 197 | 100% |
| 火锅 | 257 | 197 | 77%(`LIMIT 200` 截断所致) |

> 复现:`python scripts/bench_name_search.py`

**当前不启用 FULLTEXT 查询路径**:在 6,949 这个量级,两种写法墙钟耗时几乎一样
(都 ~280–300ms,Aura 的网络往返占绝对主导),而过程调用(`CALL db.index.fulltext.queryNodes`)
比 `CONTAINS` 更容易被 LLM 写错。索引建好留着,量级上来再切。

### 4.3 并行双路检索

混合路由下图谱和向量互不依赖,原来串行执行:

| | 耗时 |
|---|---|
| 图谱路 Text2Cypher | 1.6 – 2.0 s |
| 向量路 embedding + 检索 | ~0.3 s |
| **串行** | ~1.9 – 2.3 s |
| **并行(线程池)** | **1.3 – 1.5 s** |

总耗时等于较慢的那一路,而不是两路之和。

### 4.4 省掉语义路由下白跑的 LLM 调用

原实现在 `semantic` 路由下也会先跑一次 Text2Cypher 生成图谱查询,拿到结果后
直接丢弃换成向量结果——一次白花的 LLM 往返。

| | 语义类问题耗时 |
|---|---|
| 优化前 | 3 – 5 s |
| 优化后 | **0.5 s** |

### 4.5 三级缓存

| 层级 | 内容 | 介质 | TTL |
|---|---|---|---|
| L1 精确 | 归一化问题 + 路由 + 上下文锚点 | 进程内(全局) | 1 h |
| L2 向量 | 查询文本 → embedding | 进程内 | 24 h |
| L3 语义 | 相似问题 → 历史答案 | Neo4j `:QACache` + 内存矩阵镜像 | 72 h |

实测(线上应用):

```
第 1 次问「集宁区人均50以下的餐厅有哪些」  →  ⚡ 命中语义缓存(相似度 1.000)   ← 服务重启后 L1 已空,靠 Neo4j 里的 L3 命中
第 2 次问同一句                            →  ⚡ 命中精确缓存                    ← L1
```

**踩坑三:缓存 key 不能只 hash 问题。** Streamlit 的 `st.cache_data` 作用域是
**整个进程、跨所有会话**的。如果只按问题文本做 key,用户 A 问「集宁区火锅」后追问
「那评分高的呢」,用户 B 也追问「那评分高的呢」——两句字面完全相同、指代完全不同,
会互相串答案。所以 key 里必须带 **路由 + 上下文锚点**(上一条非追问问题);
追问取不到锚点时**直接绕过缓存**。

**踩坑四:CONTAINS 之外,缓存暴露了一个崩溃 bug。** 反馈按钮的 key 原来是
`md5(答案前 80 字 + 问题)`。加了缓存之后,同一个问题第二次返回的答案字节级完全相同,
两条消息算出同一个 ID → `StreamlitDuplicateElementKey` 直接崩页。
这个 bug 之前就在(内容哈希做消息 ID 本身就是错的,用它做反馈落库的 MERGE 键
还会让不同用户的赞/踩互相覆盖),只是缓存让"答案相同"从偶发变成必然才触发。

### 4.6 LLM 输出控制

答案生成用 `temperature=0.3, max_tokens=400`(提示词要求答案 200 字以内,
400 token 不会截断);Text2Cypher 保持 `temperature=0.1` 保证语句稳定。

## 五、功能

- **对话式问答**:多轮追问、流式输出、推理路径、检索路径、来源标注、结果表分页 + CSV 导出
- **对比分析**:「集宁区和四子王旗的餐饮对比」→ 自动生成对比表 + 条形图
- **指标看板**:三方案评测对比、分类型命中率、缓存命中率、反馈好评率、点踩 badcase 列表
- **对话历史**:存在 Neo4j,刷新不丢;右上角「🕘 历史」可切换/新建会话
- **反馈闭环**:每条回答下可赞/踩,点踩必须填具体意见,落库后在指标看板汇总
- **地图分布**:区县热力 + 点击下钻,浏览器端完成
- **图谱探索**:ECharts 力导向图,区域总览 / 商家邻域两种模式
- **商家查询**:区县/品类/评分/人均/关键词多条件筛选

### 对比分析的识别方式

「火锅店和咖啡厅对比」这类意图**不用正则切分**。中文实体名没有词边界,
`(.+?)和(.+?)对比` 会把「四子王旗」切成「四」+「子王旗」。
改成拿图谱里真实的区县/细类/商圈名单做子串匹配:一句话里出现同一类的两个真实实体,
才算对比意图。

> 已知局限:两边必须都是图谱里的真实实体名。说「烧烤店」时若图谱里没有这个细类名,
> 不会被识别成对比,会退化成普通检索。

## 六、踩坑记录

除了上面 4.1–4.5 里的四个,还有:

1. **WSL 里的 Neo4j 和线上的 Aura 是两份数据。** 菜品实体(`:Dish`)只在本地库跑过,
   没同步到 Aura,而提示词里已经写了 `(POI)-[:招牌菜]->(Dish)`。
   结果是问「哪里有卖羊杂的」会生成 `MATCH (p:POI)-[:招牌菜]->(d:Dish)`,
   在线上匹配不到任何东西——**返回 0 条且不报错**(Neo4j 对不存在的标签不报错),
   用户看到的是"没找到"而不是错误。静默失败比报错更难发现。
   已用 `scripts/extract_dishes.py` 重新同步(468 个菜品 / 2,969 条关系)。

2. **展示文案必须和执行逻辑一致。** 检索路径面板原来写的是
   "RRF 倒数排名融合 → LLM 精排取 Top-5",但线上 hybrid 路由实际走的是
   "图谱优先 + 向量补位去重",既没有 RRF 也没有 LLM 精排。
   `rrf_fuse` / `rerank_with_llm` / `hybrid_retrieve` 三个函数**从未被调用过**——
   是死代码。展示和执行不一致,面试一问就穿。已改成按真实合并逻辑描述。

3. **`RETURN count(p)` 的结果不能按店名判定。** 评测计数题时,
   结果集是 `[{数量: 1623}]`,按"标准答案是否出现在 Top-5"判定会得到 0 分,
   把正确回答误判成完全失败。计数题要单独按数字判定。
